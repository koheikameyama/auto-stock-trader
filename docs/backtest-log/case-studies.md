### 事例: パニック底反発の live 実装 (2026-07-15, KOH-554)

**★教訓の核心: 「BT で検証済み」は「本番で再現できる」を意味しない。本番の情報集合で測り直すまで、実装してはいけない。**

**発端**: 出口の磨き上げが済み「残るは live 実装だけ」の状態だったが、雛形 (`us-etf-monitor.ts`) を写経する前に本番の情報集合を確認したところ、**BT が使っている値が本番 15:24 に存在しない**ことが判明した。

**問題1 (最重要): breadth / N225 の参照日が1営業日ずれる。** BT は `dailyBreadth.set(day, ...)` を**その日の終値**で作り (`breakout-simulation.ts:107`)、エントリー判定も `dailyBreadth.get(today)` を見る (`combined-simulation.ts:217`)。しかし本番の `MarketAssessment.breadth` は朝8:02 に `calculateMarketBreadth()` が「DBにある最新JP営業日」を採るため**前営業日終値ベース**。`^N225` も DB は前営業日まで。**当日 breadth を 15:24 に知るには全3,000銘柄のライブ時価が必要で、立花の負荷ルール (8:00-15:30 は大量取得を控える) に真っ向から反するため、ラグは技術的に消せない**。

→ **この乖離は panic 固有ではなく GU/PSC/ETF/buyback すべてに既に存在する系統的なもの** (`combined-simulation.ts:980` のコメントが本番側のラグを認識している)。ただし GU/PSC の breadth≥54% は緩慢なレジームフィルタなのに対し、**panic の breadth<40% は暴落中に急速に動くので最もラグに敏感** → panic だけは実装前に測り直した。

**測り直し (`--entry-lag 1` = 「D の終値で判定 → D+1 の引けで買う」= live で完全再現できる唯一の定義)**:

| 窓 | baseline | +panic lag0 (BT既存定義) | **+panic lag1 (live再現)** |
|---|---:|---:|---:|
| fullcycle 2019-01〜2026-04 | 73.2 | 82.5 (+12.7%) | **91.2 (+24.6%)** |
| D期 2024-03〜 | 75.9 | 71.7 (-5.5%) | 70.0 (-7.8%) |
| +buyback joint | 59.7 | 87.3 (+46%) | **68.4 (+14.5%)** |

(Calmar = NetRet/MaxDD。¥500K、現エンジン)

**結果: 1営業日ラグは戦略を殺さない。むしろ fullcycle では lag0 を上回る** (1日待つ方が底に近く拾え、MaxDD も 21.7%→20.6%)。buyback レッグは panic の有無で PF 1.84 のまま不変で、「資金需要のタイミングが直交して食い合わない」が live 再現定義でも成立。

**⚠️ 絶対値は却下リストの記録 (fullcycle Calmar 4.74) と全く違う**。却下 #39 のエンジン修正と #12 の PSC trail 0.3 化によるもの。`--intrabar-model end-of-bar` で回すと NetRet +149.3% となり記録の +149.2% にほぼ完全一致することを確認済み (測定系の健全性確認)。**同一エンジン内の相対比較でのみ判断すること**。

**問題2: breadth の母集団が違う。** BT は `maxPrice<=2500` に絞ったユニバース、本番 `calculateMarketBreadth()` は JP全銘柄 (低breadth帯で約2pp差)。40% 閾値は BT 定義で較正されているので、**`MarketAssessment.breadth` は流用せず `src/core/panic/market-state.ts` で BT と同じ定義を SQL 再計算する** (判定は前営業日の確定終値なので DB クエリのみ・API負荷ゼロ)。厳密には BT のユニバースは「期間中どこかで ≤2500」(未来情報込み) で live は「その日の終値が ≤2500」しか作れないが、`--breadth-universe daily` で両者を突き合わせた結果 **22件中21件一致・残り1件も同一エピソード内で1営業日ずれるだけ・combined BT の結果は1桁まで完全一致**。

**問題3: 雛形の us-etf-monitor は BT が適用している DDハルトを無視している。** BT は `etfShouldTrade = ddHalt.shouldTrade` (`combined-simulation.ts:951`) で週次5%/月次10%ハルトを panic/ETF レッグにも掛けるが、`us-etf-monitor` は breadth しか見ていない。**暴落3日目 (=発火日) はまさに週次DDが出ている局面**なので、写経すると BT が撃たない日に本番だけ撃つ。`calculateDrawdownStatus()` を呼ぶこと (`MarketAssessment.shouldTrade` は breadth<54% で常に false になるため流用不可)。

**問題4: 固定SL戦略のSLが約定時に-3%へ潰される (KOH-555 で別PR)。** `recalculateExitPrices()` が `validateStopLoss()` を無条件に通し、3%超のSLを一律クランプしていた。**panic と buyback Phase B の両方をブロックする既存バグ**で、これを直さないと「-12%固定SL・SL到達ゼロ」は再現しない。SL逆指値の期限が11暦日固定で20営業日を保有しきれない問題も同時に修正 (⚠️ 立花の `sOrderExpireDay` は**最大10営業日**なので期限内の更新は必ず入る。`ensure-broker-sl` の retryCount が通算回数で数えていたため、正常な期限更新3回で上限に達し以後SL無しになる状態だった)。

**live↔BT パリティの検算 (`scripts/_verify-panic-parity.ts`)**: 本番が 15:24 に実行する経路 (`getPanicMarketState()` + `detectPanicSignal()`) を過去の各営業日に回し、BT のイベント集合と突き合わせた。**BTイベント日±3営業日の140日を走査して20/20 完全一致・周辺120日で誤発火ゼロ**。これが「BT で検証済み」を live で担保する唯一の手段なので、条件を触ったら必ず再実行すること。

**⚠️ ローカルで検証する時の落とし穴（対処済み）**: ローカルPostgresの既定TZが `Asia/Tokyo`、本番は `Etc/UTC` で、`@db.Date` を JS の Date と**等値比較**する Prisma クエリ (`calculateMarketBreadth(asOfDate)` 等) が**ローカルだけ 0件を返す**問題があった（パリティ照合が全140日 `unavailable` になって発覚）。**2026-07-15 に `ALTER DATABASE auto_stock_trader SET timezone = 'Etc/UTC'` で本番に揃えたので、現在は追加設定なしで動く**。詳細と再発時の対処は `.claude/rules/date-handling.md`「前提: DBセッションのタイムゾーンは UTC」。

**★測定時のもう1つの罠**: Bash ツールのシェルは **zsh** で bash と違い変数を単語分割しない。`BB="--enable-buyback ..."` を `$BB` で渡すと**フラグが黙って無視され baseline と同じ数字が出る**。「効果なし」と誤結論しかねないので、**フラグは必ずインラインで書き、効いた証拠の行 (`ポジション枠: ... + PANIC1`, `[data] パニック底反発 シグナル: N件`) を grep して検算する**。

**本番構成の留保 (B-2)**: BT の `--enable-panic` は `--enable-etf` と排他 (panic は ETF レッグを間借りする実装) なので、測ったのは **GU+PSC+panic** で本番の GU+PSC+us-etf+panic とは違う。ただし **us_etf は本番稼働 (2026-05-21) 以降一度も約定しておらず** (本番DBで0ポジション確認済)、実際の食い合いリスクは現状ほぼゼロと判断して先に進めた。ETF が実際に発火し始めたら panic 専用レッグを立てて4本立てで測り直すこと。

### 事例: minAvgVolume25 の本番/BT 乖離 — 測ったが決められなかった (2026-08-03)

| 平均の窓 | `computeAvgVolume(historical, 25)` = 真の25日平均 | `summary.volumeAnalysis.avgVolume20` = **20日平均**（名前は avgVolume25 だが実体は20日） |

**スイープ実測 (`--compare-min-avg-volume`, 2024-03〜2026-07, ¥500K, SMA50ゲートON)**:

| minVol | Trades | PF | MaxDD | NetRet | Calmar |
|---|---:|---:|---:|---:|---:|
| 30,000 | 387 | 2.66 | 13.2% | 462.9% | 14.46 |
| **50,000 (本番実態)** | 387 | 2.66 | 13.2% | 462.9% | 14.46 |
| 75,000 | 393 | 2.69 | 13.2% | 457.9% | 14.27 |
| **100,000 (BT既定)** | 391 | 2.61 | 12.7% | 399.1% | 12.93 |
| 150,000 | 389 | 2.94 | 12.7% | 592.3% | 19.21 |
| 200,000 | 387 | 2.78 | 18.2% | 649.5% | 14.72 |

1. **30,000 と 50,000 が完全一致 = このゲートは 50,000 以下では1銘柄も弾いていない**。`minTurnover ¥100M` × `maxPrice ¥2,500` から **avgVolume は算術的に最低 40,000 必要**で、流動性の選別は実質 turnover ゲートがやっている。minAvgVolume25 が効くのは価格 ¥1,000 超の銘柄だけ (実際、監査で落ちた5件はすべて ¥1,472〜2,515)
2. **閾値を 6.7倍振ってもトレード数は 387〜393** = 選別力がほぼない
3. **NetRet は 399%〜592% と大きく振れ、しかも非単調** (100,000 が6水準中で最下位、両隣の 75,000/150,000 が上)。トレード数がほぼ同じで結果だけ跳ねるのは**数件の入れ替わりが複利で増幅された経路依存ノイズ**。150,000 の Calmar 19.21 に飛びつくのは「単発BTの優位はWFで確認するまでノイズ」の典型で却下

**判定: 50,000 と 100,000 のどちらが良いかはこのデータでは決められない。** SMA50 が全窓一貫で -66% だったのとは性質が全く違う。したがって**性能を理由にした変更はできない**。揃えるとしたら理由は整合性のみ — BT と本番でユニバースが違うと、今後 BT で最適化しても「本番が売買していない銘柄群」の上で最適化することになり、SMA50 と同じ失敗モードが静かに積み上がる。

**対応 (2026-08-03): 整合性のみを理由に本番を BT 側へ寄せた。性能改善は主張しない。**

判断の根拠は損得の非対称性。揃えて外した場合の損失はほぼゼロ (トレード数 387→391、差は 150,000/200,000 が示したノイズ帯の内側) で、しかも**厳しくする方向なので新しいリスクが開かない**。一方で揃えなければ、今後 BT で何を最適化しても「本番が売買していない銘柄群」の上で最適化し続けることになる。効くのが価格 ¥1,000 超の帯 = 実際のエントリーの大半が居る場所なので、主要な判断装置に恒常的な測定誤差が乗る。SMA50 の乖離が4ヶ月生き延びて実際に損を出したことが、放置コストの実例。**Calmar 19.21 で最良に見えた 150,000 には行かない** (トレード数が同じで結果だけ跳ねる = ノイズ)。

実装: `GateInput.minAvgVolume25` を任意引数で追加 (既定は従来の `SCORING.GATES.MIN_AVG_VOLUME_25` で後方互換 = スコアリング系に影響なし)、`checkGates` の唯一の呼び出し元 `gu-watchlist-builder` からのみ `min(GAPUP, PSC)` = 100,000 を渡す。併せて分母も `computeAvgVolume(historical, 25)` から `summary.volumeAnalysis.avgVolume20` に変更し、**流動性ゲートと出来高サージ倍率の両方**が BT と同じ分母を使うようにした (サージ倍率は 25日平均→20日平均でわずかに厳しくなる方向)。

最小値が 100,000 直上に切り上がっており、ゲートが意図通り binding していることを確認。スイープ実装 `--compare-min-avg-volume` は再現用に残置 (フラグOFFで baseline 完全不変)。

### 事例: PSC が combined で機能していない — 原因は「枠の奪い合い」ではなく銘柄衝突 (2026-08-03)

**★教訓: 共有プールの食い合いを見たら、必ず「何が共有されているか」をコードで確認してから原因を書くこと。枠・現金・銘柄・cooldown は別物で、остальные を混同すると誤った対策に進む。**

SMA50 の乖離を直した後の combined BT で、**PSC レッグだけが PF 1.08 / 純損益 -¥56,540** と全体 (PF 2.61 / +399%) から浮いていたので調査した。

**(1) PSC 単体は健全**: 2024-03〜2026-07 の単体BT で **426トレード / PF 2.31 / 期待値 +2.23% / MaxDD 7.3% / +117.3%**。WF (7窓) も **OOS集計PF 2.08・判定 堅牢✓** (IS/OOS 1.60、全窓アクティブ)。戦略としては生きている。
※ 副次: WF の最適 `atrMultiplier` は 1.2 / 1.0 / 0.8 と**不安定**で、本番値 0.8 は7窓中1窓でしか選ばれない (4窓が 1.2)。ただし「不安定」判定なので追うのは同じノイズの罠。

**(2) combined では 426シグナル中 126 しか約定できず、質も落ちる** (PF 2.31 → 1.08)。

**(3) パラメータ起因ではない**: `--compare-psc-trail` で 0.3〜1.5 を振っても PSC レッグは PF 0.82〜1.41 / 5中4がマイナス。直近 KOH-552 の trail 0.5→0.3 は無関係。

**(4) 「PSC が GU の枠を奪う」は誤り (要訂正だった仮説)**: スロットは `guPositions.length < limits.guMax` / `pscPositions.length < pscMaxPos` で**完全に分離**、`limits.totalMax` も未設定なので `totalUnderLimit()` は常に true。GU/PSC 間で共有されているのは次の3つだけ:
- **`cash`** — さらに `riskAmount = cash × risk%` なので、他戦略が現金を握ると**建てられなくなるだけでなくサイズも縮む**。T+2 の `pendingSettlement` で返却も遅れる
- **`allOpenTickers`** — 同一銘柄の二重保有禁止
- **`lastExitDayIdx`** の cooldown 3日 — **戦略をまたいで共有**（cooldown の趣旨が「同銘柄の構造的リピート回避」なので銘柄単位で横断に効くのが設計として正しい。バグではない）

**(5) 対照実験で寄与を切り分け**: 予算を100倍 (¥50M, `--max-price 2500` でユニバース固定) にして cash 制約を外しても GU の取りこぼしは消えない。

| 予算 | GU (PSCあり) | GU (PSC 0) | 差 |
|---|---:|---:|---:|
| ¥500K | 265 | 309 | -44 (-14.2%) |
| ¥50M | 378 | 408 | -30 (-7.4%) |

→ **約3割が現金の食い合い、約7割は銘柄衝突** (資金無限でも消えない30件)。**GU と PSC は同じ小型株ユニバースを相関したトリガーで狩っており、同じ銘柄に同じ日に発火する**（本番でも 2026-06-30 の 3989.T が GU・PSC 両方で発注されている）。補完でなく実質 substitute で、KOH-511「発生ソースは相補的でも capital は substitute」と同じ構図が GU/PSC 間で起きている。

**(6) 処理順は BT/本番で一致**: BT は GapUp (`combined-simulation.ts:1361`) → PSC (`:1463`)、本番も `worker.ts` の `runEntryMonitors` が `gapup → psc → us-etf → panic`。**乖離ではなく意図した設計**。

**(7) この窓では PSC を外す方が良い、が採用しない**:

| 予算 | GU3+PSC2 | GU3のみ | 差 |
|---|---:|---:|---:|
| ¥500K | Calmar 12.93 (+399.1%) | **16.19 (+509.6%)** | +25% |
| ¥50M | Calmar 18.55 (+577.1%) | **21.10 (+638.1%)** | +14% |

方向は資金規模に頑健だが**撤去しない**。理由: ① 単発BTで WF 未確認 (プロジェクト鉄則)、② この窓は D期偏重で GU が異常に強い局面 (PF 2.82/+410%) であり、**PSC の価値は offseason にある可能性をこの窓では測れない**、③ **本番DBは 2024-02-13 以降しかなく fullcycle 検証が物理的に不可能** (却下#21 等の fullcycle 検証はローカルの 2018+ backfill DB を使っている)。

**次にやるなら**: (a) ローカル backfill DB で offseason を含む fullcycle の `GU3のみ vs GU3+PSC2`、または (b) PSC の実弾トレードを貯めて forward で判断。実装は `--compare-split-positions` に単独構成行 (GU/PSC 片側のみ) と Calmar 列を追加したのみで本番影響なし。

### 事例: PSC を停止し GU 単独構成へ + サイジング乖離の発見 (2026-08-03)

**★教訓: 「単体で有効」と「共有プールで足す価値がある」は別物。そして構成比較をする前に、BT のサイジングが live と同じ基準かを必ず確認すること。**

上記「PSC が combined で機能していない」の続き。判断の前に**本番DBの制約（2024-02-13以降しかない）を外す**ため、ローカルに fullcycle 環境を構築した。

**(0) ローカル fullcycle DB の構築 (再現手順)**: `createdb auto_stock_trader` → `npx prisma migrate deploy`（localhost なのでルール上OK）→ 本番から `Stock` を `\copy` で複製（pg_dump は client 14 / server 17 の version mismatch で不可）→ yfinance で **2018-01-01〜2026-07-31 の 6,988,218本を8分で投入**（`^N225` / `^VIX` 含む）。約2GB。seam を作らないよう 2024年以降も含めて単一ソースで取り直している。**本番DBは一切触っていない**（前回 Railway の容量が飛んだため）。

> ⚠️ 本番DB (2024-02-13〜) で 2024-03 開始のBTを回すと、ウォームアップ80本が足りず**序盤4ヶ月がほぼ空**になる。同一窓でもローカル 528トレード vs 本番DB 391トレードと差が出た。**2024年前半を含む窓の測定はローカルDBで行うこと。**

**(1) 判定を汚染していた4つ目の乖離 — ポジションサイジング**: BT は `riskAmount = cash × risk%`（現金基準）だが、**live の `entry-executor.ts:395` は `effectiveCapital × risk%`（総資産基準、`getEffectiveCapital()` = 買余力 + 投資中(簿価) + 発注中）**。この差は複数ポジション保有時にだけ現れ、cash基準は保有が増えるほど後続のサイズを縮める = **BT は複数戦略構成に構造的なペナルティを課す**。`--equity-based-sizing`（既定OFFで baseline 完全不変）を実装して両基準で測り直した。

**(2) 結論は交絡を潰しても不変** (fullcycle 2018-04〜2026-07, ¥500K):

| 構成 | cash基準 Calmar | **総資産基準 Calmar** |
|---|---:|---:|
| GU3+PSC2 (旧本番) | 52.11 | 26.88 |
| **GU3のみ** | **67.86 (+30%)** | **34.57 (+29%)** |
| GU5のみ | 67.37 | 41.52 |
| PSC2のみ | 5.15 | 5.14 |

年代別 (総資産基準) も GU 単独が**一度も負けない**: 2018-2020 **3.59** vs 2.26 / 2021-2023 1.47 vs 1.46 (同点、GU5なら1.82) / 2024-2026 **17.61** vs 16.50。データソース (本番DB/ローカル)・サイジング基準・資金規模 (¥500K/¥50M)・年代のすべてで方向が一致。

**(3) SMA50 フィルターは GU 単独でも有効** (ユーザー指摘で確認。構成が変われば前提も変わるため必須の再確認だった): fullcycle・総資産基準で GU3のみ **34.57 (ON) vs 22.89 (OFF) = +51%**、GU5のみ +79%、GU3+PSC2 +144%。MaxDD も ON が良い (19.2% vs 21.4%)。**どの構成でも ON が正しい。**

**対応**: `POST_SURGE_CONSOLIDATION.ENTRY_ENABLED = false`（Exit は常に稼働するので保有中ポジションは通常決済）。**併せて BT の `defaultLimits.pscMax` も 2→0** に揃えた — 片側だけ変えると SMA50 と同じ乖離を再生産するため。`MAX_POSITIONS_PSC` はエントリーゲートでしか使われないので値は据え置き（再開時にそのまま効く）。PSC を含む構成は `--compare-split-positions` で引き続き測れる。

**留保（過信しないこと）**: ① **サバイバーシップバイアス** — 2018-2023 のユニバースは現在の `Stock` マスタなので途中で上場廃止になった銘柄が不在。両アームに等しく効くので比較は成立するが**絶対リターンは楽観側**。② **複利の誇張** — +5,000% は ¥500K→¥26M で非現実的（実運用capacityは¥5-10M）。意味があるのは比率のみ。③ ポートフォリオ構成の問いに WF は適用できない（WFは戦略単位）ので、年代3分割を代替エビデンスとした。

**未処理の宿題**: **記録済みの Calmar 値はすべて cash基準サイジングで計算されている。** fullcycle baseline で 52.11 → 26.88 と半減するため、BT既定を総資産基準に変えて再ベースライン化するかは別途判断が必要（却下リストの一部の結論、とくに「補完戦略は食い合う」系は cash基準のペナルティで強調されていた可能性がある）。また **GU3 → GU5** は総資産基準の全窓で GU5 ≥ GU3 と有望だが、別の変更なので個別検証が必要（今回はバンドルしていない）。

### 事例: サイジング既定を総資産基準へ + 新 baseline での枠・補完戦略の再評価 (2026-08-04)

**★教訓: 基準（baseline / サイジングモデル）が変わったら、その上で決めた値は全部“未検証”に戻る。順番は「基準を直す → 再ベースライン → 個別パラメータ」。**

**(1) サイジング既定を総資産基準に変更**（前事例で発見した4つ目の乖離の本対応）。`combined-simulation` と `gapup-simulation`（＝WFの土台）の両方で `riskAmount` の基準を `cash` から `cash + 保有ポジション簿価` へ。**`--cash-based-sizing` で 2026-08-03 以前に記録した数値を再現可能**（fullcycle 1401件 / PF 2.62 / +10,376.2% の完全一致を確認）。

**ETF は offseason 主体の2期で勝ち、D期主体の直近1期でだけ負ける**。とくに 2021-2023 では **MaxDD を 18.1% → 11.4% (-37%) に激減**させており、「GU が弱い局面で DD を埋める offseason 補完」という設計意図どおりに機能している。**→ ETF は停止しない（現状維持）。**

**★なぜ fullcycle が誤誘導したか（方法論として重要）**: fullcycle の Calmar は複利で効くため、リターンが桁違いに大きい直近期（era3 は era1/2 の約10倍）に事実上重み付けされる。**offseason 補完の価値は「GU が稼げない期間の Calmar / MaxDD」に出るので、複利加重の fullcycle 単発では構造的に過小評価される。補完戦略の判定は必ず年代別（またはレジーム別）で行うこと。** PSC 撤去の判断は fullcycle と年代別3期の**両方**で同じ向きだったので結論は変わらない。

**panic** は -2% / +10% / +17% / fullcycle +28% で 3期中2期＋fullcycle でプラス、唯一の負けも -2% とノイズ水準。**現状維持（本番稼働継続）で問題なし。**

**残る留保**: ETF dip は fullcycle で -38% と大きく負けたが年代別は未測定。ただし ETF（本番稼働中）と枠を共有する実装なので、仮に年代別で良くても ETF との joint 検証が別途必要。なお ETF は 2026-05-21 の本番稼働以降まだ一度も約定していない。**→ 2026-08-04 (KOH-600 / 却下#57) に年代別を測って決着: dip は全窓で負け (fullcycle -26% / offseason 主体の 2021-23 で -59%)、joint 検証も不要になった。**

**ローカル fullcycle DB の落とし穴**: 指数ETF (`1321`/`1545`/`1547`) は `Stock.tickerCode` が **`.T` 無し**で保存されているため、tickerCode をそのまま yfinance に渡すと解決できず**バーがゼロ件で入る**。ETF/panic が黙って0トレードになり原因が分かりにくい。yfinance には `<code>.T` で問い合わせ、DB には bare code で入れること。

### 事例: GU/PSC「1日1件制限」撤廃 → 枠まで複数エントリー（2026-07-03, KOH-505）

**契機**: 本番 GU スキャンで 4812.T(¥2,718, サージ5.77x)・4722.T(¥1,683, 1.54x) の2件がヒットしたが、首位 4812.T が集中率上限（1単元が資金50%超）で棄却され、**次点 4722.T は評価すらされずノーエントリー**に終わった。原因は `gapup-monitor.ts` / `post-surge-consolidation-monitor.ts` の `triggers.slice(0, 1)`（1日1件制限）。首位が資金都合で弾かれても次候補にフォールバックしない。

**判明した本番↔BTの構造的乖離**:
- **本番**: `slice(0,1)` で1日1件 + entry-executor が集中率50%チェック
- **combined BT / gapup・PSC 単体BT**: どちらも `maxDailyEntries` 未設定＝**枠(GU3/PSC2)まで当日複数エントリー**。combined BT は `maxDailyEntries` を一切参照していない
- → combined BT の全成績（Calmar 47 等）は「枠まで複数」前提で出ており、**本番だけ1日1件に絞られていた**。旧コメント「1日1件で PF 2.45→2.73」は gapup **単体WF**の話で、資金無限の理想値。CLAUDE.md 鉄則「正式判断は combined」に照らすと単体WFで判断していたのが誤り

**検証（`--compare-daily-entries` を combined-run に追加、本番影響なしフラグ）**:

単体WF（複数 vs 1件、`--max-daily-entries=1`）:

| | GU複数 | GU1件 | PSC複数 | PSC1件 |
|---|---:|---:|---:|---:|
| OOS集計PF | 2.15 | 2.53 | 2.58 | 2.56 |
| OOS平均PF | 3.26 | 3.07 | 2.99 | 2.81 |
| **IS/OOS比** | **0.99** | 1.39 | **1.00** | 1.21 |
| 総トレード | 273 | 140 | 271 | 141 |

→ 単体では per-trade PF は1件がやや上だが、**複数の方が IS/OOS比 ~1.0 で過学習なく頑健**。トレード数は複数が倍。

combined（正式判断基準、¥500K、GU/PSC の1日上限をスイープ）:

| 設定 | PF | MaxDD | NetRet | **Calmar** |
|---|---:|---:|---:|---:|
| **複数（枠まで, BT既定）** 長期2024-03〜 | 3.92 | 6.0% | +283.7% | **20.31** |
| GU=1/PSC=1（**旧本番**） 長期 | 3.06 | 10.6% | +178.0% | **7.16**（最下位） |
| GU=2/PSC=2 長期 | 3.85 | 6.6% | +292.7% | 19.07 |
| GU=複数/PSC=1 長期 | 3.98 | 6.6% | +289.5% | 18.69 |

- **正式判断基準の長期combined(28ヶ月)で、旧本番(GU=1/PSC=1)が全構成中ダントツ最悪**（Calmar 7.16, MaxDD 10.6%）。複数化(枠まで)で **Calmar 20.31 / MaxDD 6.0%** に激変
- 直近12ヶ月(D期偏重)の単発BTでは逆に「GU=1/PSC=複数」が最良に見えたが、**長期では複数(枠まで)が最良**。これは CLAUDE.md 鉄則「単発BTの優位はWFで確認するまでノイズ」の典型例。GU複数化が12ヶ月で悪く見えたのは D期特有のノイズだった

**判定: 1日1件制限は害。GU/PSC とも枠まで複数エントリーに統一（当初の狙い＝4722.T のような次点取りこぼし防止も自動達成）。**

**実装**（`gapup-monitor.ts` / `post-surge-consolidation-monitor.ts`）:
- `slice(0,1)` を撤廃し全トリガーをループ。トリガーは holdingTickers（保有＋当日pending買い）除外済み・優先度降順ソート済み
- 空き枠 = `MAX_POSITIONS_GU/PSC − 既存open/orderedポジ数` を算出、成功ごとに `slotsLeft--`、0で当日確定。同一ループ内の枠超過を防ぎ、二重建ては holdingTickers 除外で別途担保、executeEntry内の枠チェックも保険
- 失敗の分類: **枠上限/現金残高不足/予算不足/日次損失制限** = 当日打ち止め(break)、**集中率上限/投資比率上限/セクター/SLクランプ等の銘柄固有** = 次候補へ継続、**例外(catch)** = 一時障害で次分再試行。`result.retryable:true` は全て構造的発注不可、真の一時障害は例外側という分離を利用
- BT比較モード `--compare-daily-entries`（combined-simulation の `guMaxDailyEntries`/`pscMaxDailyEntries` + combined-run の比較ブロック）は再現用に残置（フラグ未設定で baseline 完全不変、commit 9eea86ab で先行マージ済み）

「直近N件の PF / WinRate / DD% が閾値割れでサイズ縮小」案も検討したが、**SMAフィルターと同じ遅行指標メカニズム**のため同じ失敗パターンになる可能性が高い。採用見送り。

### 実装として残したもの（本番への影響なし）

バックテスト側のみ、以下を残置（検証の再現性のため）:

- `combined-simulation.ts`: `equityCurveSmaPeriod` を Breakout 限定から全戦略(GU/WB/PSC)に拡張
- `combined-run.ts`: `--compare-equity-filter` モードにレジーム別内訳を追加
- `combined-run.ts`: ctx の `equityCurveSmaPeriod` デフォルトは **0（無効）**。Phase 0拡張で全戦略に適用されるようになったため、20のままだと常時SMA20フィルターがONになり基準BTの結果も悪化する事象を確認（2026-04-22追加修正）

### 今後のレジーム適応に関する方針

- **既存機構で十分**: breadth band 55-80% と日経SMA50 と VIXレジームフィルターで、A〜E 各レジームで許容可能なパフォーマンスは既に確保できている
- **ローリング系スロットルは採用しない**: 短期決戦戦略では遅行指標として機能しない
- **レジーム適応で改善したい場合の正攻法**: (1) mean-reversion 系戦略の追加による戦略多様化、または (2) 2018〜2022年のバックフィルデータで A期タイプを複数サンプル取得してから再検討
- **今回の +¥13K → +¥13K 維持が "成功"**: Calmar 9.37 は現状で十分、余計な手を入れないことが正解

アクティブ運用では集中が起きる時は「強いセクターに便乗すべき時」で、機械的に切ると機会損失。分散リスク管理は以下の状況で初めて意味を持つ:

- ポジション数が20-30件以上(ETF/mutual fund水準)
- シグナル品質が低く"ランダムに拾う"モード
- レバレッジ高く単一セクターショックで破綻する水準

GU/PSC/WB/MOMを最大10枠で組合せる本プロジェクトではいずれにも該当しない。

## VIXレジーム別リスク%の可変化（2026-04-22実施、既定変更）

**結論: 既定を `elevated=0.5, high=0.25, crisis=0` に変更。既存実装の high=1.0 は暗黙のバグで、CLAUDE.md の「高ボラでサイズ縮小」コンセプトと矛盾していた。24ヶ月BTで high レジームは未発生のため既存BT結果への影響なし（保険的変更）。**

### 背景

既存実装は `if (todayRegime === "elevated") quantity /= 2` のハードコードで、`high` レジーム(VIX 25-35)では full size のまま走っていた。crisis(VIX>35)はエントリー停止されるが、high は素通し = 意図しない高リスクエントリー。

### 検証

```bash
npm run backtest:combined -- --compare-vix-risk --start 2024-03-01
```

`SimContext.riskScaleByRegime?: Partial<Record<RegimeLevel, number>>` を追加し、5パターンで比較:

| パターン | Trades | PF | MaxDD | NetRet | Calmar |
|---|---:|---:|---:|---:|---:|
| **規定(0.5/0.25)** | 289 | **3.66** | **9.0%** | **+180.3%** | **9.37** |
| 旧規定(0.5/1.0) | 289 | 3.66 | 9.0% | +180.3% | 9.37 |
| 厳格(0.25/0.125) | 282 | 3.26 | 10.1% | +149.6% | 6.89 |
| 緩和(0.75/0.5) | 266 | 3.47 | 11.5% | +163.3% | 6.62 |
| 一定(0.5/0.5) | 289 | 3.66 | 9.0% | +180.3% | 9.37 |

### 発見

- **規定 vs 旧規定 vs 一定 が完全同一** = この24ヶ月期間で high レジームが一度も発生していない
- レジーム別内訳でも A/C/E 期は全パターン同じ、B/D期でのみ elevated が一部発生
- **elevated=0.5 がこの期間では最適**(厳格・緩和どちらもCalmar劣化)
- high 閾値の最適化は長期データ(2020 COVID, 2022金利急騰期)が必要

### 既定値の決定

新既定: `{ elevated: 0.5, high: 0.25, crisis: 0 }`

- **BT期間では完全に無害**(high未発生で差分ゼロ)
- **将来の high 相場で保守的**(従来は full size だった場面で 1/4)
- CLAUDE.md の「リスク管理: 損切りラインの自動設定、連敗時の自動ポジション縮小」コンセプトと整合
- "バグ修正" 的位置づけ(明らかに意図せざる挙動を正しく制御に修正)

### 実装変更

- `src/backtest/combined-simulation.ts`: `getRegimeRiskScale()` ヘルパー追加、`SimContext.riskScaleByRegime` オプション追加、5戦略の hardcoded `elevated` 処理を可変化
- `src/backtest/combined-run.ts`: `--compare-vix-risk` 比較モード追加

本番コード(trading-*.ts / watchlist-builder / entry-executor)は BT側から独立しており、本変更の影響を受けない。運用側でも同様のレジーム別scalingを適用したい場合は別途実装が必要(本変更はBTのみ)。

### 追記（2026-04-22）: 本番側にも VIX scale を適用

BT と本番の乖離を解消するため、`getRegimeRiskScale()` を共有ヘルパー化し、本番の `entry-executor.ts` のリスク計算にも適用:

- `src/core/market-regime.ts`: `getRegimeRiskScale(regime, custom?)` を export（BT/本番共通）
- `src/backtest/combined-simulation.ts`: local copy を削除して import に差し替え（挙動変化なし）
- `src/core/breakout/entry-executor.ts`: `todayAssessment.vix` から regime を判定、`streakAdjustedPct × regimeScale` で最終リスク%を算出
  - elevated: 0.5x / high: 0.25x / crisis: 0(エントリー停止) / normal: 1.0x
  - 連敗スロットル(既存 LOSING_STREAK.SCALE_FACTOR)と VIX scale を乗算合成
  - regime scale適用時は console.log で明示

`gu-watchlist-builder.ts` のサイズ事前チェックは regime scale を適用しない(watchlist を過剰に絞る副作用を避けるため、本番発注の実サイズ決定は entry-executor で一元管理)。

**変更の意義:**
- BTで検証した `elevated=0.5, high=0.25` がそのまま本番でも効く
- 従来は本番で elevated時も full size → 本番挙動が BT結果より高リスク寄りだった
- 本変更により BT と本番の挙動が一致 = BT結果が信頼できる予測値になる

## 連敗スロットル(B3)検証（2026-04-22実施、不採用）

**結論: 不採用。Phase 0のエクイティSMAフィルターと同じ失敗パターン。全パターンで Calmar 悪化。**
**GU/PSC の短期決戦では、決済済みトレードWinRateベースのsoft reductionも遅行指標として機能しないことが確定。**

CLAUDE.md の運用示唆「月次WinRate<40%でサイズ縮小」を実装版で検証。Phase 0 ではエクイティSMAの binary halt が逆効果だったが、本検証は **トレードベース(決済済みのみ)の soft reduction(halt ではなく縮小)** で挙動が改善するかを確認。

### 実装

- `SimContext.loseStreakScaling?: { window, threshold, scale, minSample }` を追加
- `getStreakScale()` ヘルパー: 直近N件の全戦略合算 WinRate が threshold未満なら scale倍で縮小
- 5戦略の entry quantity 計算で `regimeScale × streakScale` を合成

## cooldownDays 調整(A3)検証（2026-04-22実施、現状最適を再確認）

**結論: 現状の cooldownDays=3 が最適。副次的発見として 0日運用では MaxDD 21.6% で壊滅することを確認、**
**cooldownは「構造的に有効な防御機構」であり B3/Phase 0 の遅行指標系スロットルとは別性質と判明。**

GU/PSC の cooldownDays=3 が WF で選ばれた値だったが、明示的な比較検証はしていなかった。

## RSI Oversold Bounce 戦略の検証と棄却（2026-05-02実施）

**結論: 棄却。mean-reversion 系は2024-2026の日本株（特に大型株）で構造的に機能しない。再検討禁止。**

A期（平穏ボックス相場）の弱点補完を目的に、大型株向けRSI mean-reversion戦略を実装してBTで検証。

### エントリー条件（検証時）

- RSI(14) < 30（売られすぎ）
- 直近5日リターン ≤ -5%（短期下落確認）
- 当日陽線（リバウンド開始）
- 200日SMA上（長期上昇トレンド中の押し目）
- ユニバース: 時価総額 ≥ ¥10B〜100B、価格 ≤ ¥100,000
- SL: ATR×1.5 or -7%、タイムストップ 5/7日
- 出口: SL/BE/トレール + RSI > 50で利確（mean-reversion完了）

### 検証結果（24ヶ月、2024-03 〜 2026-04、本番DB ¥500K）

| Variant | 条件 | tr | WR | PF | 期待値 | NetRet |
|---|---|---:|---:|---:|---:|---:|
| **A: 厳格** | RSI<30, -5%, SMA200, mcap≥100B | 23 | 17% | **0.13** | -2.40% | -12.8% |
| B: 緩和1 | RSI<35, -3%, SMA200, mcap≥10B | 86 | 27% | 0.20 | -1.51% | -28.0% |
| C: 緩和2 | RSI<35, -3%, SMA100, mcap≥10B | 105 | 28% | 0.21 | -1.54% | -31.1% |
| D: 緩和3 | RSI<40, -3%, SMA100, mcap≥10B | 140 | 31% | 0.25 | -1.29% | -34.5% |
| E: maxPos=3 | C と同条件 + 枠拡大 | 113 | 27% | 0.22 | -1.43% | -31.2% |

### 構造的失敗の論理

1. **全パターンで PF < 0.25**（1円勝つのに4-8円失う）= mean-reversionが成立していない
2. **緩めるほど負ける**（NetRet -12.8% → -34.5%）= 埋もれたエッジを発掘したのではなく、ノイズに突っ込んでいる証拠
3. **勝率17-31%**（mean-reversion標準55%+を大幅に下回る）
4. **WF検証は不要**（過学習以前の問題、IS/OOS両方で負ける）

### なぜ機能しないか（プロ分析）

- **2024-2026の日本株は continuation 相場が強い**（AI/半導体トレンド、大型株モメンタム優勢）
- **大型株のRSI<30到達は通常"真の悪材料"**（決算ミス、ガイダンス引き下げ、海外株安連鎖）→ 反転ではなく続落
- **「陽線で反転確認」は1日のノイズ**で、翌日続落が多い
- **A期の負けは別途 breadth band 55-80% 追加で既に解決済み**（NetPnL +¥13K黒字化、2026-04-21検証）

### 今後の禁止事項

以下のアイデアは本検証結果により**再検討禁止**:

- RSIベースの mean-reversion（RSI<30, RSI<35, RSI<40 全て負ける）
- 5日下落 + 陽線リバーサル系（緩めても改善しない）
- Bollinger Band下限tap → リバウンド系（同じ構造的失敗が予測される）
- 5日連続陰線後の陽線リバーサル系（同上）

mean-reversion 系を再検討する場合の最小限の前提条件:

- **市場環境が変化したことの実証**（例: 日経が trend → range に明確に転換した時期 6ヶ月以上）
- **別期間（2018-2022）のbackfillデータでpilot試験を先に実施**
- **A期相当のサンプルが20件以上集まる長期データ**で先に有意性を確認

それ以前にRSI/BB/連続陰線系のmean-reversion戦略を新規実装するのは時間の無駄。
